# Original cross-OS executable continuation

Run complete original application executables in Space and verify their own
output and file operations. The full application goal remains open.

The first new target is upstream flat assembler g at
`905f6791f6777e35baec182e6843e2ada30cedd0`. Its repository ships an original
Linux x86_64 ELF, Windows i386 PE32 console executable, and macOS x86_64
Mach-O. Preserve all original bytes and the upstream BSD notice. Require the
compiler itself to assemble real input files and compare exact generated bytes,
including error exits and repeated resource cleanup; its banner alone is not
completion. Existing original Linux jq/Lua/SQLite/BusyBox remain regressions.

The Windows binary imports nineteen KERNEL32 functions and has separate code,
BSS and read-only data. It requires a genuine x86 compatibility-mode CPU
activation. A distinct native context tag now owns 32-bit
register/selector/address rules, with a bounded PE32 edge
over the existing native owned address space and CPU context objects. Its
stdcall capsules only stop the activation; checked heap/file/clock work runs
after kernel-root restoration. Keep the existing PE32+ and 64-bit CPU admission
rules intact. Unknown imports and unsupported metadata must still be refused.

The initial real-application continuation passes 65 original Windows
activations: help, successful macro/arithmetic assembly and 42 actual invalid-
source/missing-file error exits. Twenty-one repeated cycles preserve native
free frames, heap high water, domain/capability counts and VFS descriptor
availability. The generated file contains exactly `Space\n` followed by four
little-endian words `257,514,771,1028`. Six malformed-image controls use a
separate test copy, never modified original executable bytes. The local receipt
is `/workspace/fasmg-win-expanded/report.json`; frozen-source verification and
regressions follow before publishing this checkpoint.

`windows-pe32-image.in` validates the separate PE32 profile and all nineteen
known imports before native allocation. `windows-pe32-memory.in`,
`windows-pe32-files.in` and `windows-pe32-services.in` own foreign heap/token,
ASCII root-file, stdcall and clock policy. `windows-pe32-process.in` owns the
bounded synchronous activation over native UserAddressSpace/CPU objects. No
second VM/frame ledger or ambient raw SCI export is introduced. This remains a
private kernel-linked integration library, with a four-MiB process arena,
explicit empty environment, preferred-base loading and no TLS/SEH/other DLLs.
It is not a general Windows installation or desktop launch service.

The upstream macOS binary uses classic indirect symbol pointers and UNIXTHREAD
startup, with thirteen libSystem imports. Its low preferred image/BSS range
overlaps the current supervisor trampoline windows. This needs a real address
space/entry solution or another original app profile; never skip pages, rewrite
the payload or claim entry after a loader refusal. Keep macOS jq's existing
modern-image/dependency boundary as separate ongoing work.

Implementation and test receipts will record exact source/compiler/application
hashes, actual CPL3 entry, output bytes, file bytes, exit/fault/budget behavior
and cleanup. Fixture control executions remain separately counted from original
application executions. Private native helpers gain no raw SCI export.
